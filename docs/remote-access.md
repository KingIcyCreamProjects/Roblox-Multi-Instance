# Remote access (Devices)

The Devices tab lets you see and control your other computers that run RMI: their screen, mouse and keyboard. Everything goes over your own Tailscale network. Nothing is put on the internet.

The wire protocol is shared with HomeLab and lives in [remote-protocol.md](remote-protocol.md). Both apps use the same viewer file (`public/remote-viewer/remote-viewer.js`, copied byte for byte from HomeLab; see "Shared viewer" below).

## Set it up

On every computer:

1. Install Tailscale and sign in with the same account. The Devices tab shows these two steps (the same ones as the friend remote, without Funnel) until Tailscale runs.
2. Install RMI.

On each computer you want to control:

3. Open Settings, Remote access. Switch on "Allow remote access" and press Save. Nobody can switch this on for you: it is only written by this computer's own Settings page, never over the network. On Windows the firewall may ask whether RMI may use the network: allow it (private networks are enough). If that prompt was dismissed, Windows blocks the port and the other computer shows "Remote access is off or RMI is not running"; allow RMI in Windows Security, Firewall, "Allow an app through firewall". Only Windows and macOS can be controlled; Linux has no hosting (the section is hidden there) but can view and control your other computers.
4. Choose "Show pairing code". The code is 8 characters, works once and expires after 5 minutes.

On the computer you sit at:

5. Open Devices. Computers running RMI with remote access on show "Ready to pair". Press Pair and type the code. The sheet then says "Paired with ..." with Connect and Done. The code is gone from the other computer's Settings once used (or after 5 wrong tries).
6. Press Connect.

Pairing happens once. The token survives restarts and updates of both apps; nothing asks for a code again unless the pairing is removed on either side. Remove (in Devices) asks first, because connecting again then needs a new code shown on that computer. If the other computer removed this one, the next Connect ends with "Pairing was removed on ... Pair again." and the Pair button comes back.

Phones, tablets and Linux computers are listed as "Can't be controlled from RMI", at the end. A computer someone else is connected to shows "In use"; Connect still works and the viewer can offer to take over.

## What paired computers tell each other

A computer you paired (it holds a pairing with another of your computers) tells that computer, every 15 seconds, which of its Roblox accounts have a client open: the accounts' Roblox user ids and the computer's own name, nothing else. The other computer answers with the same about itself, so one pairing works both ways. Each side keeps the last report for 45 seconds and uses it in two places: the [friend remote](friend-remote.md) page names the computer an account runs on ("On Office PC") instead of "On another computer", and the Accounts list and Devices tab offer "Run here". Nothing is sent to a computer you did not pair with, and nothing while the vault is locked (a locked computer answers with an empty list). A Linux computer can report this way too, because it only has to send.

**Run here** moves a running account to this computer: the paired computer closes that account's Roblox client (auto-relaunch, the watcher's reconnect and the automation API there leave it closed until someone launches it there by hand), then this computer launches it into its own saved destination (else Roblox's home screen), never the Play bar's. Run here is refused while a launch runs here; a launch that starts during the wait goes first and the moved account is queued behind it. An account whose session expired or was never signed in here is not moved. An account the other computer is launching itself at that moment is not closed there (it stays there). Two Run heres to the same computer while it is still asked join into one. Only accounts saved in RMI on both computers move; they are matched by Roblox user id, and no cookie or other secret crosses the network. From the computer that holds the pairing the request goes straight to the other one. From the other side it rides the answer to the next report, so it takes up to 15 seconds. The other computer must report within 20 seconds to be asked at all, and after 40 seconds without an answer the request gives up. Run here and Run on start only while this computer's vault is unlocked; a lock while they wait ends them (`VAULT_LOCKED` / `VAULT_WAS_LOCKED`) and nothing launches here. Removing a pairing drops that computer's reports and any ask still waiting for it. Run here fails, and nothing closes, when the other computer runs an older RMI ("Update RMI on Office PC first.") or is locked ("RMI is locked on Office PC."; a locked computer that holds the pairing stops reporting, so its accounts soon stop showing as running there).

**Run on** sends an account the other way: pick a paired computer and that computer launches it like Play there (its own saved destination on that computer, else Roblox's home screen). The account must be saved in RMI on that computer, matched by Roblox user id. It works for an account running here, on a third computer, or nowhere. The other computer is asked first, and only the accounts whose client really started there are then closed wherever else they run (here included, for good: auto-relaunch leaves them closed). It follows its launch for up to 15 seconds; what has not started by then is cancelled and stays where it was, as does an account whose session expired there. An account already past the point its launch can be cancelled is watched for 120 seconds more, and a client of it that shows up late is closed again, so it never runs in two places. A computer without Roblox (on Linux: Sober, with pasta) is not offered. Run on refuses while a launch runs here, and does not send an account running on a computer whose older RMI cannot close it (the reply's `old` names that computer, which must update first). If an account could not be closed where it ran, RMI says so: it runs in two places until closed there. The request travels like Run here: straight away from the computer that holds the pairing, else with the answer to the next report, and the other computer then confirms in a report of its own. It must report within 20 seconds to be asked; after 40 seconds without that confirmation nothing is closed. While such a send waits for its confirmation, another to the same computer fails at once ("Office PC is still taking the last accounts. Try again in a moment."). A send fails, and nothing closes, when the other computer runs an older RMI ("Update RMI on Office PC first."), is locked ("RMI is locked on Office PC."; a locked computer that holds the pairing does not report, so the send ends with "Office PC did not answer. Is RMI open there?"), or has none of the accounts saved ("Those accounts are not saved in RMI on Office PC.").

## Files and sound

- **Files** ("Allow file transfer", off until you switch it on): the viewer can browse this computer's folders (starting at your home folder), download files, and send files here. Files sent here always land in your Downloads folder under their own name, never anywhere else; a file that is already there is never replaced (`photo (1).jpg`). Only the base name is kept: folders, characters Windows refuses (`< > : " | ? *`), device names like `CON` or `COM1` (saved as `_CON`), and trailing dots and spaces are dropped, and names are cut to 150 bytes of UTF-8 (about 50 characters in Chinese or Japanese; the extension stays). At most 4 GB per file and 2 transfers at a time. While it arrives it is written as `name.part` and renamed when complete, so a quit or crash never leaves a partial file under the real name. A file that did not arrive whole (cancelled, failed, or the session ended) is deleted. Not available in view only. Every transfer is listed in Recent sessions ("2 files sent, 1 file received", the files on expand).
- **Sound** ("Allow sound", on by default, Windows only for now): the viewer can listen to what this computer plays (its default output device, followed when you switch devices). Off until the viewer asks. Sound is never held back: if the connection is slow, it drops sound rather than delaying the picture or input.

Switching either off removes it from what this computer offers to new sessions and refuses new requests. In a running session it also takes effect within 2 seconds: sound stops, and running transfers end ("File transfer was switched off on the device.").

## While a session runs

- The controlled computer shows a small always-on-top bar, "... is viewing this computer" (or "is controlling" once input or a folder listing or file transfer was used), with Stop. Closing that bar also stops the session.
- Settings, Remote access shows who is connected with a Stop button, and keeps the last 20 sessions (who, when, how long, view only or control, and the files sent and received).
- After Stop at the device, new sessions are refused for 30 s ("Stopped at the device.").
- One session at a time. Another paired computer is told who is connected (`busy`, with `by`) and may ask to take over, which ends the current session (`replaced`). The same computer connecting again (its old connection died unnoticed) always replaces its own stale session.
- When the session ends for any reason, input still queued (the rest of a long paste) is dropped and every key and mouse button the viewer held down is released. RMI waits up to 0.5 s for that before the next session may start; input still being typed past then (a long `text`) can finish after it. Quitting or updating RMI ends a live session the same way first (at most 1 s).
- Stop also counts when no session is live yet (one taking over at that moment is refused).
- The viewer can switch to view only; input is then ignored.
- Switching remote access off, or removing the paired computer, ends a live session at once.
- The viewer pings every 2 s. If nothing arrives for 10 s (the viewing computer slept, crashed or lost the network), the session ends and everything held is released.
- Plugging in or removing a monitor does not end the session: the viewer gets the new list (`screens`) and keeps the same screen if it is still there, else the primary one. An empty monitor list (display asleep, a failed enumeration) is ignored; input pauses until monitors are back.
- With two or more monitors the viewer can show all of them in one picture (screen 255).
- If this computer's Tailscale address changes, the session ends and RMI listens on the new address (checked every 15 s).
- A paired computer that has left the tailnet stays in Devices as Offline, with Remove.
- While the session window is open, keys go to the other computer only: RMI's own shortcuts (Ctrl+L lock, Ctrl+Shift+H, Ctrl+K) do not fire, but typing still counts as activity for the idle auto-lock. The title bar and window buttons stay usable; the tabs do not switch until the session window closes.

## CSP trade-off

The main window's CSP has `connect-src ws:` so the shared viewer can open the session socket straight from the webview (on macOS to the loopback relay described above, which passes the socket's bytes through unchanged). That lets any script in the main window open a plain WebSocket to any host, not just a tailnet peer on port 7813; CSP cannot name the peers because their addresses are only known at run time. We keep it for v1 because the webview loads only RMI's own bundled code. The tighter alternative is a relay: Rust opens the socket and passes messages to the webview over IPC, so `ws:` can leave the CSP, at the cost of an extra hop for every frame.

## Differences from remote-protocol.md

- **Off**: the protocol says an off host refuses the socket with state `off`. RMI does more: when off there is no listener, so the connection is refused at TCP level and `hello` does not answer. A socket that reaches the host in the moment it is switched off gets `state: off` and `bye`.
- **Extra endpoints**: `GET /v1/remote/hello` (no auth: `{app, proto, name, busy}` only; `busy` is true while a session is live, so Devices can show "In use"), `POST /v1/remote/pair` (`{code, name}` to `{token, name}`), `POST /v1/remote/running` (`{name, userIds, canHandOver, canLaunch}` with the Bearer token of a paired computer, only from the IP it paired from: which accounts have a client there, so the friend page can name the computer an account is on; `canHandOver` and `canLaunch` are left out by an older RMI, which then never gets a queued hand-over or send; right after acting on a queued send the report also carries `launched: [ids]`, the ids whose client started there, and `launchedOp`, the `launchOp` of the answer it acts on (a `launched` list whose `launchedOp` does not match the waiting send is ignored as late); `canLaunch` is false where Roblox cannot be launched (and while locked); answered with `{name, userIds, canLaunch}` about this computer, plus `handover: [ids]` once when Run here here wants those accounts closed there and `launch: [ids]` with `launchOp` (a number naming that send) once when Run on here wants them launched there; an older RMI answers `{}`), `POST /v1/remote/handover` (same auth; `{userIds}`, at most 256, to `{released}`: the ids with no client left after closing them for good; `409` code `locked` while the vault is locked, `503` while RMI is still starting, `404` from an older RMI) and `POST /v1/remote/launch` (same auth and limits; `{userIds}` to `{started}`: the ids whose client started within 15 s, like Play; ids not saved there are left out; `409` code `locked`, `503`, `404` from an older RMI). The protocol leaves auth app-specific.
- **Caps**: `hello` lists `screens`, `cursor`, `stats`, `takeover`, `media` and `all`, `h264` when the machine has an H.264 encoder, plus `files` (unless "Allow file transfer" is off) and `audio` (Windows, unless "Allow sound" is off). Never `secure`: RMI runs as a normal user process. `all` is listed even with one monitor, since one can be plugged in mid-session; the viewer offers All screens only with two or more. `screens` entries always carry `x`,`y`. A `screens` message is sent only when the monitor list changes (the viewer's own `start` already says which screen streams).
- **`bye`** carries `code` and an English `why`. Codes RMI sends: `stopped` (Stop or the bar closed, and for 30 s after), `off`, `removed` (the paired computer was removed or evicted), `auth` (missing or unknown token, or the token used from another IP), `busy` (with `by`, the connected computer's name), `timeout` (nothing from the viewer for 10 s), `network` (this computer's Tailscale address changed), `replaced` (taken over, or the same computer connected again or paired again). Never `offline` or `old`.
- **`stats`** is sent every 2 s while streaming in every quality; only `auto` adapts. `scale` is the real one: the adaptive step times the 1920 px limit (a 4K screen at step 1 reports 0.5). `fps` and `kbps` count what was actually sent; `cap` and `enc` are the average grab and scale+encode ms, `kb` the average frame size, `inflight` the frames waiting for an `ack`, `w` the sent width. `codec` is `h264` or `jpeg`; H.264 sends its target `br` (kbit/s) and `encoder` (`NVENC via MF`, `AMD AMF via MF`, `Intel Quick Sync via MF`, `software MF`, `VideoToolbox`) instead of `q`. The viewer's Show stats line shows the codec, sent and target rate, `enc` and its own decode ms (`dec`).
- **`cur`**: Windows sends the system cursor's shape (`wait` also for the "working in background" arrow); macOS sends `default` with the position only. `vis` is false while the pointer is hidden or outside the streamed screen.
- **`takeover`** works only for a paired computer with a valid token; it is refused during the 30 s after Stop like any other session.
- **`combo`**: `hello` lists the supported ones in `combos` (RMI: `["lock"]`). `lock` locks Windows (`LockWorkStation`) or macOS (Ctrl+Cmd+Q). `cad` is ignored: a normal process cannot send Ctrl+Alt+Del.
- **Keys**: besides the `media` keys, the JIS keys `IntlRo`, `IntlYen` and `KanaMode` are handled. Korean Hangul/Hanja keys are not.
- **Terminal** (`0x03`, `term`): not offered (`"terminal": false`); `term` messages are ignored.
- **Limits**: `maxFps` is clamped to 1..60, wheel to plus or minus 1200 per message, key codes to 32 characters; the viewer sends typed text in chunks of at most 1000 characters (a long paste arrives as several, typed in order), but the host types any `text` that fits in a message; text messages at most 8 KB (larger ones are ignored, and refused as `auth`); binary messages from the viewer at most 256 KB + 5 bytes and only after auth (a larger one closes the socket).
- **`files`**: `fs` replies carry `"parent":null` at a drive or file system root; there is no drive list. Entries follow links (a broken link is listed as itself); `mtime` is in seconds. Errors are short English sentences (`Not found.`, `Access denied.`, `That is not a folder.`, `Use a full path.`). Paths must be absolute (`""` is the home folder). A download's header, chunks and `done` travel in order behind control messages, sound and frames; a viewer `ack` may come at any time (the host keeps at most 4 MB unacknowledged). An upload sends `got` every 1 MB and once more before `done`; one that ends short, runs past its `size`, or runs more than 6 MB ahead of `got` fails with `err` and is deleted. A cancel by the viewer gets no reply. `fs` and new `get`/`put` are refused in view only and when "Allow file transfer" is off (`err`); `ack`, `end` and `cancel` always pass. The host lets transfers already running continue when view only is switched on, but the shared viewer cancels its own running transfers at that moment ("Stopped. View only is on."), so in practice they stop. Transfer ids are `u32`; an id still running is refused. A file is logged when its transfer starts (download: the file name and size; upload: the name it was saved as and the announced size).
- **`audio`**: the rate is the output device's own (usually 48000 Hz); at most 2 channels (a surround device sends its first two). With no output device, or one whose format cannot be sent, the host answers `{"t":"audio","on":false,"err":"..."}` once and stops until the viewer asks again. Messages are exactly 20 ms. A new `{"t":"audio","rate","ch"}` is sent when the default output device changes, and sound queued in the old format is dropped. Nothing is sent while nothing plays (Windows sends no loopback data then). Sound keeps playing in view only.

## Things that cannot work

As in the protocol: UAC prompts, the Windows lock screen and windows running as administrator cannot be seen or clicked. While one is up the viewer shows "Locked". Controlling the lock screen, sign-in and UAC (`secure`) needs a system service; that is HomeLab only, RMI never offers it. macOS needs Screen Recording and Accessibility permission for RMI, granted at the Mac. Sound is Windows only for now (not offered on macOS).

Anti-AFK, if on, does not count remote input as you being active (Windows marks it as injected), so it may still nudge Roblox during a long session.

## Shared viewer

`public/remote-viewer/remote-viewer.js` and `.css` belong to HomeLab. `src/features/devices/viewer.test.ts` fails if they differ from the hashes in `viewer.sha256.json`. To take a new version:

```
node tools/sync-remote-viewer.mjs <path to the HomeLab checkout>
```

Then run the tests and commit both files with the new hashes. The viewer's colours come from RMI's tokens through the `--rv-*` variables in `src/styles/index.css`.

## Test it on two computers

Automated tests use a fake screen and a recording input; they never move the real mouse. To try it for real:

1. Build or install this version on two computers signed in to the same Tailscale.
2. On computer B: Settings, Remote access, switch on, Save. Check the status line shows "On as ..., at 100.x.y.z:7813". Choose Show pairing code.
3. On computer A: Devices. B shows "Online, Ready to pair". Pair with the code: the sheet says "Paired with B". B's Settings now lists A under Paired computers and no longer shows the code.
4. Connect. Check: B's screen appears with the pointer; B shows the always-on-top bar ("A is viewing", then "A is controlling" after the first click); moving and clicking on A moves B's pointer; typing (letters, Shift, arrows, Enter, a volume key) and the wheel work; Ctrl+L typed in the session does not lock RMI on A; switching screens and the all-screens picture work on a multi-monitor B; unplugging a monitor on B keeps the session.
5. Hold a key or mouse button on A and close the viewer: nothing stays held on B.
6. Press Stop on B's bar: A shows the session ended; Connect again within 30 s is refused. B's Settings shows the session in Recent sessions.
7. Lock B (Win+L): A shows "Locked". Unlock at B: the picture comes back.
8. Quit RMI on A and B, start both again: Connect works without a code.
9. Switch remote access off on B and Save: A's live session ends; Devices on A shows B as "Remote access is off or RMI is not running".
10. Files (when the viewer offers them): browse B's home folder, download a file over 4 MB and compare it; send a file to B twice and check B's Downloads has `name` and `name (1)`; cancel a big upload halfway and check nothing is left in Downloads; switch view only on and check transfers are refused. B's Recent sessions shows "1 file sent, 2 files received".
11. Sound (Windows B): play something on B, switch sound on in the viewer, check it plays on A; switch B's output device (speakers to headphones) and check it follows.
12. On a Mac host, also check that RMI appears in Screen Recording after the first connect (allow it, restart RMI), that input starts once Accessibility is allowed without reconnecting, and the `needs_permission` message.
